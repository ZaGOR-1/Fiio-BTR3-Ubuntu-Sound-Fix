# FiiO BTR3 на Linux (Ubuntu): діагностика USB-аудіо та PipeWire

> **Практичний журнал діагностики та відтворюваний workaround.** Цей README описує випадок, коли FiiO BTR3 видно в Linux, але звук через USB DAC періодично зникає, особливо під час роботи Discord. Інструкція також містить перевірку мікрофона Lenovo/Realtek після змін у PipeWire.
>
> **Важливо:** конфігурація буфера `1024` допомогла відновити звук у цьому випадку, але її не слід вважати універсальним або остаточно доведеним виправленням. Зокрема, пізніше виникали окремі проблеми зі звуком і якістю мікрофона. Робіть зміни по одній і перевіряйте їх результат.

## Середовище та обладнання

Це **конкретна перевірена конфігурація**, а не вимоги до всіх систем:

| Компонент | Дані з діагностики |
|---|---|
| ОС | Ubuntu 26.04, GNOME |
| Аудіосервер | PipeWire **1.6.2** із сумісністю PulseAudio (`pipewire-pulse`) |
| Менеджер сесії | WirePlumber **1.6.2** |
| ALSA tools | `speaker-test` 1.2.15.2 |
| Ноутбук | Lenovo Legion Slim 5 |
| USB DAC | **FiiO BTR3**, не BTR3K |
| USB ID | `0a12:1243` (Cambridge Silicon Radio) |
| Вихід | `alsa_output.usb-0a12_FiiO_BTR3_ABCDEF0123456789-00.analog-stereo` |
| Мікрофон | Вбудований, **Realtek ALC257**, через Ryzen HD Audio Controller |
| Програми, з якими відтворювалася проблема | Discord (Snap), Chrome, ігри/Steam |

### Чому в Ubuntu написано «TaoTronics» замість FiiO?

У GNOME та `lsusb` пристрій міг з'являтися як:

```text
CSRA64210 [TaoTronics Headset BH-22 in charging mode]
Bus 005 Device 002: ID 0a12:1243 Cambridge Silicon Radio, Ltd
```

Але ALSA однозначно показувала:

```text
USB-Audio - FiiO BTR3
FiiO BTR3 at usb-0000:08:00.3-1, full speed
```

Це **не означає, що до ноутбука підключили TaoTronics**. USB ID `0a12:1243` присутній і в описі FiiO BTR3 в [ранішому Linux workaround](https://github.com/ReimuNotMoe/FiiO-BTR3-USB-Linux-Workaround). Людинозрозумілий підпис у базі USB-пристроїв може бути неточним. Для перевірки реального пристрою дивіться також `cat /proc/asound/cards` і USB-дескриптори.

## Симптоми

- Звук у FiiO BTR3 через USB періодично **повністю зникав**, хоча пристрій залишався вибраним за замовчуванням.
- Після запуску або перезапуску Discord звук міг зникнути не лише в Discord, а й у браузері та інших програмах.
- **Вбудовані динаміки ноутбука продовжували працювати** під час збою FiiO.
- У `wpctl status` аудіопотоки Chrome, Discord та інших програм були з'єднані з `FiiO BTR3:playback_FL/FR` і позначені як `[active]`, але звуку не було.
- `pactl list short sinks` інколи показував FiiO як `RUNNING`, тоді як `/proc/asound/BTR3/stream0` — `Playback: Status: Stop`. Це *стани різних рівнів*, і їх треба звіряти **в один і той самий момент під час реального відтворення**.
- У журналі PipeWire багато разів повторювалося:

```text
spa.alsa: front:1p: (125 suppressed) snd_pcm_avail after recover: Канал обірвано
```

Англійський відповідник: `snd_pcm_avail after recover: Broken pipe`. Це вказує на проблему обробки/відновлення ALSA-аудіопотоку (`EPIPE`/XRUN-подібний стан), **але за одним таким повідомленням не можна довести**, що джерело саме FiiO або саме Discord.

## Що вдалося встановити

| Спостереження / тест | Результат | Що це доводить (і чого не доводить) |
|---|---|---|
| `pactl info` | `PulseAudio (on PipeWire 1.6.2)` | Використовується PipeWire, не окремий PulseAudio daemon |
| `/proc/asound/BTR3/stream0` | `S16_LE`, 2 канали, `44100` і `48000` Гц | Такі формати декларує USB DAC |
| Примусові 48 кГц | Звук усе одно зникав | Одних 48 кГц недостатньо для цього випадку |
| Вбудовані динаміки | Працювали, коли FiiO мовчав | Загальний звуковий тракт ноутбука не був повністю несправний |
| Пряме відтворення через ALSA `hw:CARD=BTR3` | **Тестовий тон було чути** | FiiO та драйвер ALSA принаймні могли працювати без PipeWire |
| Закриття Discord + перезапуск PipeWire | Повертався звук | Перевідкриття аудіопотоків допомагало; не доводить, що корінь проблеми тільки в Discord |
| `clock.force-quantum 1024` | Тимчасово стабілізувало звук | Збільшення буфера — перспективний workaround |
| Постійний `1024 / 1024 / 1024` | Успішно застосувався в `pw-metadata` | Конфіг дійсно завантажився; тривала стабільність не доведена |
| Подальші тести мікрофона | Мікрофон повернули, але якість/шуми залишали питання | Не доведено, чи причина в буфері, рівні підсилення, драйвері або обробці голосу |

## Швидкий спосіб: перевірити буфер 1024

Перед постійною зміною **протестуйте її без редагування файлів**. Закрийте Discord, відновіть звук через перезапуск служб за потреби, потім задайте quantum:

```bash
# Якщо FiiO завис у стані без звуку (закрийте Discord перед рестартом)
systemctl --user restart pipewire pipewire-pulse wireplumber

# Тимчасово зафіксувати буфер на 1024 семплах
pw-metadata -n settings 0 clock.force-quantum 1024

# Подивитися налаштування
pw-metadata -n settings 0 | grep -E 'clock\.(quantum|min-quantum|max-quantum|force-quantum)'
```

Потім запустіть Discord, перевірте голосовий канал, YouTube, ігри й повторне відтворення після паузи. **Виправлення в конкретній системі допомогло на цьому етапі**, але надалі все одно спостерігалися інші аудіопроблеми.

Скасувати тимчасовий тест:

```bash
pw-metadata -n settings 0 clock.force-quantum 0
```

> `1024` семпли при 48 кГц — це близько **21,3 мс на блок**. Це не повна наскрізна затримка звуку. Більший буфер може підвищити стабільність за рахунок затримки, зокрема в іграх і моніторингу мікрофона.

## Зробити буфер 1024 постійним

**Застосовуйте лише якщо тимчасовий тест допоміг.** Це налаштування впливає на **весь користувацький PipeWire**, включно з мікрофоном та іншими аудіопристроями, а не лише на FiiO BTR3.

### 1. Створіть окремий конфіг

```bash
mkdir -p ~/.config/pipewire/pipewire.conf.d

cat > ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf <<'EOF_CONF'
context.properties = {
    default.clock.quantum = 1024
    default.clock.min-quantum = 1024
    default.clock.max-quantum = 1024
}
EOF_CONF
```

Не потрібно копіювати повний `/usr/share/pipewire/pipewire.conf` і не потрібно змінювати `/etc/pulse/daemon.conf`: для сучасного PipeWire є **drop-in конфігурації**.

### 2. Перезапустіть аудіослужби

Закрийте Discord та інші програми з активним захопленням/відтворенням перед перезапуском — вони можуть втратити старе з'єднання з аудіосервером.

```bash
systemctl --user restart pipewire pipewire-pulse wireplumber
```

Або перезавантажте Ubuntu після збереження відкритої роботи.

### 3. Перевірте, що конфіг застосувався

```bash
cat ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf

pw-metadata -n settings 0 | grep -E 'clock\.(quantum|min-quantum|max-quantum|force-quantum)'
```

У дослідженій системі після застосування було:

```text
clock.quantum       1024
clock.min-quantum   1024
clock.max-quantum   1024
clock.force-quantum 0
```

Це **нормально**: `force-quantum = 0`, коли значення встановлюються конфігом, а не тимчасовим примусовим override.

Якщо ви не створювали файл, а бачите `1024 / 32 / 2048 / 0`, це **не підтверджує** фіксацію 1024: `1024` може бути лише стандартним розміром буфера.

## Як скасувати налаштування

Якщо з'явився шум мікрофона, проблеми з додатками, затримка або нестабільність, **спочатку скасуйте лише власний конфіг**:

```bash
# Перейменовуємо, а не безповоротно видаляємо
mv ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf \
   ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf.disabled

# Закрийте Discord перед цією командою
systemctl --user restart pipewire pipewire-pulse wireplumber
```

Щоб повернути налаштування:

```bash
mv ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf.disabled \
   ~/.config/pipewire/pipewire.conf.d/90-audio-buffer.conf
systemctl --user restart pipewire pipewire-pulse wireplumber
```

Не запускайте одночасно декілька експериментальних конфігів, які змінюють ті самі `default.clock.*` параметри: так важко зрозуміти, яка зміна реально спрацювала.

## Діагностика, коли звук знову зник

Перевіряти бажано **під час відтворення**, коли звуку у FiiO фактично немає.

### Ідентифікація USB DAC та звукових пристроїв

```bash
lsusb -d 0a12:1243
cat /proc/asound/cards
cat /proc/asound/BTR3/stream0
```

`Status: Stop` сам собою може бути нормальним, коли жоден потік не відтворюється. Порівнюйте його зі станом **під час активного тестового сигналу**.

### PipeWire / WirePlumber

```bash
LANG=C pactl info | grep -E 'Server Name|Default Sink|Default Source'
pactl list short sinks
pactl list short sources
pactl list short sink-inputs
wpctl status
```

> Цифрові ID вузлів у `wpctl status` **змінюються** після перепідключення FiiO або перезапуску служб. Не копіюйте старі ID з чужих журналів. Для гучності поточного пристрою можна використовувати `@DEFAULT_AUDIO_SINK@` або `@DEFAULT_AUDIO_SOURCE@`.

Якщо `pactl` відсутній:

```bash
sudo apt install pulseaudio-utils
```

Це лише CLI-утиліти PulseAudio; встановлення **не означає**, що необхідно замінювати PipeWire.

### Журнал помилок

```bash
journalctl --user \
  -u pipewire -u pipewire-pulse -u wireplumber \
  --since '15 minutes ago' --no-pager | tail -n 100
```

Шукайте `snd_pcm_avail after recover`, `Broken pipe`, `xrun`, `underrun` та інші повідомлення. У цьому випадку журнал містив багато повідомлень `snd_pcm_avail after recover: Канал обірвано`.

### Швидке тимчасове відновлення

Якщо Discord закритий, а FiiO досі без звуку:

```bash
systemctl --user restart pipewire pipewire-pulse wireplumber
```

Після такого рестарту запущені застосунки можуть втратити аудіопідключення; відкрийте їх заново. Ця команда **лікує симптом**, а не доводить причину збою.

## Прямий тест ALSA без PipeWire

Цей тест потрібен, щоб відокремити програмний аудіосервер від ALSA/USB DAC. **Він успішно відтворив тон у навушниках у дослідженому випадку.**

1. Закрийте Discord, браузерні дзвінки, ігри та програми, які тримають аудіопристрій.
2. Попередьте себе про можливий гучний тестовий тон: зніміть навушники й зменште фізичну гучність FiiO.
3. Тимчасово зупиніть PipeWire, виконайте тест, потім **обов'язково запустіть служби знову**:

```bash
systemctl --user stop \
  wireplumber.service \
  pipewire-pulse.socket pipewire-pulse.service \
  pipewire.socket pipewire.service

speaker-test -D hw:CARD=BTR3,DEV=0 \
  -c 2 -r 48000 -F S16_LE -t sine -l 1

systemctl --user start \
  pipewire.socket pipewire-pulse.socket \
  pipewire.service pipewire-pulse.service wireplumber.service
```

Якщо тест повідомляє `Device or resource busy` (`-16`, `EBUSY`), хтось усе ще використовує ALSA-пристрій. Це **не** означає несправність FiiO. З'ясуйте, який процес його утримує, і не завершуйте навмання системні процеси.

Якщо тест відтворює тон, це підтверджує, що в даний момент **FiiO + ALSA здатні працювати**. Це не виключає періодичні USB/драйверні проблеми, але переносить увагу на керування потоком, буферизацію та програми.

## Мікрофон: шуми або зникнення запису

У ноутбуці використовувався **вбудований Realtek ALC257** (під час однієї перевірки — `card2`), а FiiO BTR3 був **лише виходом навушників**. Номери карт можуть змінюватися після перезавантаження.

Після експериментів із буфером мікрофон іноді переставав працювати або записував із шумами. **Точної причини та підтвердженого виправлення якості мікрофона в цій діагностиці не встановлено.** На Windows якість могла відрізнятися через іншу обробку голосу.

### Вибір джерела та контрольний запис

```bash
wpctl status
pactl list short sources
wpctl get-volume @DEFAULT_AUDIO_SOURCE@

# Якщо джерело правильно вибране, але приглушене:
wpctl set-mute @DEFAULT_AUDIO_SOURCE@ 0

# Запис 5–10 секунд; зупинити Ctrl+C
pw-record /tmp/mic-test.wav

# Прослухати (перевірте, що вихідний пристрій теж працює!)
pw-play /tmp/mic-test.wav
```

Якщо FiiO не відтворює, для прослуховування виберіть **вбудовані динаміки ноутбука**, інакше можна помилково вирішити, що запис порожній.

### Апаратне підсилення Realtek

```bash
cat /proc/asound/cards
grep -H '^Codec:' /proc/asound/card*/codec* 2>/dev/null
alsamixer
```

В `alsamixer`: `F6` → карта з **ALC257** → `F5` (усі регулятори) або `F4` (Capture). Шукайте `Internal Mic Boost`, `Mic Boost`, `Capture`.

У конкретній перевірці `Internal Mic Boost` показував **53%**, але це **не 53 dB** і не доказ причини шуму. Якщо є фон/шипіння, зафіксуйте вихідне значення, спробуйте зменшити підсилення на один крок і порівняйте два записи при однакових умовах. Зменшення може зробити голос тихішим. Не змінюйте відразу всі повзунки.

Якщо запис у `pw-record` чистий, а в Discord шумний — перевіряйте налаштування обробки голосу Discord (Noise Suppression, AGC, Echo Cancellation) та обране джерело. Якщо шумний і локальний запис — починайте з ALSA/рівнів мікрофона, а не з перевстановлення Discord.

## Що не допомогло або не було підтверджено

- **Лише 48 кГц:** `pw-metadata -n settings 0 clock.force-rate 48000` успішно застосовувалося, але звук і далі зникав. Відоме старе рішення для BTR3 на 44,1 кГц **не пояснює весь цей випадок**.
- **Автоматичне призупинення через WirePlumber:** обговорювалося `session.suspend-timeout-seconds = 0` тільки для FiiO, але його ефективність у цій історії **не підтверджено**. Не додавайте цей параметр без окремого тесту.
- **`api.alsa.headroom`:** це документований спосіб змінити додаткову буферизацію **конкретного ALSA-вузла**; він потенційно кращий за глобальні обмеження, якщо виникає конфлікт із мікрофоном. Але в цій системі значення для FiiO **не підбирали й не перевірили**.
- **Остаточна причина:** Discord неодноразово запускав сценарій збою, але не доведено, що саме він є єдиним дефектним компонентом. Також не доведено апаратну несправність BTR3.
- **Жорстке `1024 / 1024 / 1024`:** значення було коректно застосовано й допомогло, але надалі виникали питання якості/роботи мікрофона і повторні збої відтворення. Це **workaround**, не гарантія.

Для подальших експериментів із FiiO-специфічними параметрами дивіться [офіційну документацію ALSA у WirePlumber](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html), розділ про `monitor.alsa.rules`, `api.alsa.headroom` та `session.suspend-timeout-seconds`. Не копіюйте значення для іншого обладнання без перевірки.

У цьому випадку прямий ALSA-тест працював, аудіослужби тимчасово відновлювали звук, а буфер `1024` був корисним workaround. Для повторюваної стабільності та якості мікрофона потрібні подальші окремі тести; глобальне налаштування слід легко мати можливість скасувати.
